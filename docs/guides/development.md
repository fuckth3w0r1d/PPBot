# 开发与运行指南

本指南说明当前源码的构建、配置、s0 部署和验证方法。当前聊天功能使用单个多模态聊天模型、独立文本判定与 embedding 服务，以及按群隔离的近期时间线和 SQLite 消息归档。待开发需求及其验收要求见 [需求规格](../spec.md)。模块和数据关系见 [架构说明](../map.md)，其他文档见 [导航](../README.md)。

## 构建环境

需要支持 C++17 的 `g++`、C 编译器、GNU Make、OpenSSL 开发头文件及库、线程库，以及启用 FTS5 的 SQLite 开发头文件与库。Fedora 可安装 `sqlite`、`sqlite-devel`，Ubuntu 可安装 `sqlite3`、`libsqlite3-dev`。仓库已包含 `include/httplib.h`、`include/json.hpp` 和 [sqlite-vec](https://github.com/asg017/sqlite-vec) 0.1.6 源码；sqlite-vec 随程序编译，不需要单独部署扩展或数据库服务。

s0 的部署基准为 Ubuntu 24.04、x86_64 和 GLIBC 2.39。本地构建产物需要兼容目标机器的处理器架构和动态库，上传后的加载检查见下文部署步骤。

在项目根目录执行：

```sh
make
```

构建自动收集 `src/` 下的 `.cpp`，以 C++17 和 `-O2` 编译，同时编译 sqlite-vec 的 C 源码，将对象文件与依赖文件保存在 `release/` 对应目录，链接 `ssl`、`crypto`、`pthread` 和 `sqlite3`，生成 `release/bot`。`make clean` 会删除整个 `release/` 目录。仓库现有二进制不能替代本地源码构建的验证。

sqlite-vec 的 C 源码使用 `-fno-math-errno`，允许编译器将不读取数学 `errno` 的向量运算内联为机器指令。该参数不保证不同系统之间的全部动态库兼容性；面向 s0 的构建仍需检查目标机器能否加载产物。

聊天功能的本地模拟验收执行：

```sh
make test
```

该目标编译并运行 [聊天验收](../../tests/chat_test.cpp)、[日志验收](../../tests/logging_test.cpp)、[归档验收](../../tests/archive_test.cpp) 和 [停机验收](../../tests/stop_test.cpp)，产物位于 `release/tests/`。测试使用本地 HTTP 模型、embedding 和 NapCat 模拟服务、HTTP/HTTPS 外部命令模拟服务及真实 SQLite，检查命令入口、参数、回复引用与类型、成功或失败发送的历史记录，以及图片选择、引用、token 预算、流式正文与回拍、判定和概率分流、旧功能停用、事务归档、迁移、检索边界、错误日志和密钥脱敏；停机验收向子进程发送真实 `SIGTERM`、`SIGINT`，检查最终入库及失败退出状态，不需要真实模型密钥。固定返回的模型标签和向量只验证程序行为，真实识图、语义判定、检索相关性和 QQ 送达按下文手工验证。

## s0 部署与实测更新

项目部署在服务器 `s0`，通过 `ssh s0` 连接。NapCat 和服务配置已经就绪。更新程序前先核对下文的模型配置：`chat_llm` 需要支持图文输入及 SSE 流式返回，`judge` 是独立文本判定服务，`embedding` 是独立 OpenAI 兼容向量服务。示例中的服务地址、模型和密钥均为占位值，必须填写实际配置。普通插话概率由 `chat_llm.reply_probability` 控制，默认及示例为 `0.1`。

已有配置需将原 `ai` 块改名为 `chat_llm`，保留块内配置值；当前版本只读取 `chat_llm`。尚未迁移归档功能的配置还需添加 `embedding` 块，将原 `ai.context_bytes`、`judge.context_bytes` 换成以 token 为单位的 `chat_llm.context_tokens`、`judge.context_tokens`，并按需要填写 `chat_llm.retrieval_context_tokens`。字节与 token 的单位不同，预算需按新单位设置。旧的 `context_bytes`、原 `ai.max_rounds` 和 `ai2` 不再读取，不能继续用于控制预算或总结。部署机器需要提供启用 FTS5 的 SQLite 运行库；Ubuntu 对应 `libsqlite3-0`，Fedora 对应 `sqlite-libs`。仅传输二进制不会安装该运行库。

二进制使用 `scp` 经 SSH 传输本地 `release/bot`，不同步源码，不在服务器仓库执行 `git push`、`git pull` 或 `git checkout` 等代码更新操作。配置准备完成后再重启服务。

systemd 服务名为 `qqbot`，服务定义位于 `/etc/systemd/system/qqbot.service`。服务以 `r3t2` 用户运行 `/home/r3t2/PPBot/release/bot`，即 `~/PPBot/release/bot`；工作目录为 `/home/r3t2`，配置中的相对文件路径以该目录为基准。标准输出和标准错误写入 journal。

本地构建环境需要与 s0 的处理器架构和动态库版本兼容，包括 SQLite。首次升级前，确认原有群时间线已经完成周期保存，并按下文“数据目录与停机”检查迁移条件。随后在本地项目根目录执行：

```sh
make &&
scp release/bot s0:~/PPBot/release/bot.new &&
ssh s0 '/lib64/ld-linux-x86-64.so.2 --list /home/r3t2/PPBot/release/bot.new'
```

构建成功后才上传产物。上传文件暂存为同目录的 `bot.new`，先用 s0 的动态加载器检查依赖。确认输出中没有 `not found`、版本缺失等错误后，再执行替换和重启；不能只凭该检查命令的退出码判断兼容性。存在错误时，保留现有程序，使用与 s0 兼容的构建环境重新编译。

```sh
ssh s0 'mv ~/PPBot/release/bot.new ~/PPBot/release/bot && sudo systemctl restart qqbot'
```

通过重命名替换二进制，避免直接覆盖正在执行的文件。更新后查看服务状态和日志，并按本文“手工验证”中的场景检查实际回复：

```sh
ssh s0 'systemctl status qqbot --no-pager'
ssh s0 'sudo journalctl -u qqbot -n 100 --no-pager'
```

## 配置文件与加载路径

以下用于首次准备运行环境；已有部署按模板核对聊天、判定和 embedding 服务配置。模板的实际文件名是 [config.example.json](../../config.example.json)。从项目根目录准备配置：

```sh
cp config.example.json config.json
```

复制后还不能直接启动。当前 [config.h](../../include/config.h) 中 `load_config` 的默认路径是 `/home/r3t2/PPBot/config.json`，[main.cpp](../../src/main.cpp) 没有传入其他路径。程序不会自动读取当前工作目录中的 `config.json`，也没有命令行或环境变量覆盖入口。必须将配置放在该路径，或者在开发时修改头文件中的默认路径后重新 `make`。

配置解析直接读取各项字段，缺少字段、类型不符或 JSON 无法解析可能导致启动失败。所有配置块都需要按 [config.cpp](../../src/config.cpp) 的读取方式提供；当前没有关闭某一功能后省略对应配置的机制。修改配置后需要重启进程。

| 配置块 | 用途与填写要求 |
| --- | --- |
| `log` | 日志文件路径、文件与控制台级别；级别为 0 DEBUG、1 INFO、2 WARN、3 ERROR，输出配置级别及以上日志 |
| `bot` | `qq` 使用字符串，与 NapCat 机器人账号一致；`name` 为模型输入中的机器人名称，默认 `Bot` |
| `server` | NapCat HTTP API 的主机、端口、访问令牌；PPBot 通过 HTTP 调用该地址 |
| `client` | PPBot 接收上报的监听地址与端口；`access_token` 会被读取，但不执行入站校验 |
| `chat_llm` | 唯一多模态聊天模型；包含地址、模型、密钥、静态提示词、预算、超时和插话概率，示例服务需替换为实际配置 |
| `judge` | 独立判定服务；必须提供 `host`、`path`、`model`、`key`，另有独立端口、超时和短上下文预算 |
| `embedding` | 独立 OpenAI 兼容 embedding 服务；必须提供 `host`、`model`、`key`，`port` 默认 443，`path` 默认 `/v1/embeddings`，`timeout_seconds` 范围 1 到 60 秒、默认 3 秒 |
| `amap` | 天气服务主机、HTTPS 端口、请求路径和密钥 |
| `b23` | 卡片应用 ID、B 站 HTTPS 主机和查询、播放路径 |
| `file` | 缓存与数据路径、单次下载字节上限、缓存文件数量、下载缓冲字节数、保存间隔秒数 |
| `random_img` | HTTPS 图片服务，响应需要 `url` 字段 |
| `random_img2` | HTTP 图片服务，代码在路径后附加 `?tag=`，响应需要 `proxyUrls` 字符串数组 |
| `eat` | HTTPS 餐食服务，响应需要 `mealwhat` 字段 |
| `music` | HTTP 音乐搜索与直链服务，依次读取 `result.songs[0].id` 和 `data[0].url` |

示例中的密钥和文件路径必须按运行环境填写。`random_img2` 的示例与 `random_img` 指向相同服务，但二者的客户端协议和响应字段要求不同，不能据此认定两个图片命令都可用；实际配置需匹配代码要求。其他外部服务同样依赖响应格式，示例地址不代表服务已经验证可用。

`chat_llm` 与 `judge` 都使用 Chat Completions 格式。`host` 可填写带 `http://` 或 `https://` 的主机地址，省略协议时使用 HTTPS；没有显式端口时使用对应 `port`，API 路径单独填写在 `path`。主聊天服务需要接受由 `text` 和 `image_url` 组成的混合内容，并可访问 NapCat 上报的 HTTP(S) 图片 URL。所有 `chat_llm` 请求均设置 `stream=true`，服务须以 `text/event-stream` 返回 SSE 事件，通过 `choices[0].delta.content` 提供正文增量，并用完整的 `data: [DONE]` 事件结束。文字、图文和拍一拍使用同一流式协议。仅支持文本或非流式返回的服务不满足聊天配置要求。

接收端会聚合跨网络分片的事件、JSON 和 UTF-8 字符，只保留正文，不发送思考或用量统计。QQ 端等待 HTTP 请求成功且收到完整结束事件后，才发送一次完整聊天回复。中断、超时、无效事件或缺少结束信号不产生半截回复：直接唤醒尝试发送失败提示，普通路径沉默。不自动重试或回退为非流式；输出达到 token 上限时保留既有截断告警。

`judge` 保持非流式，请求体显式包含 `{"thinking":{"type":"disabled"}}` 关闭思考，判定服务须接受此字段。`judge.max_tokens` 默认的 16 token 预算用于输出 `YES` 或 `NO` 短标签，不用于思考。判定只接收文本、媒体类型标记及可用文本，不接收图片或图片 URL。`YES` 表示当前应由本机器人回应，`NO` 表示没有明确需要回应，后续仍进入概率筛选；判定失败也走同一概率筛选，不重试，不调用聊天模型代判。判定结合近期上下文、发言对象、消息语义和机器人人设，话题相关、命中关键词或仅提及机器人不足以要求回复。

`embedding` 接受 OpenAI 兼容请求，提交 `model`、文本 `input` 和 `encoding_format: "float"`，响应需在 `data[0].embedding` 返回非空、有限数值组成的非零向量。向量维度从响应确定并校验，不需要另填维度。服务地址或模型变化后，后台从保留期内原文重建向量；同一服务模型突然返回不同维度时报告错误。该服务只处理原文及检索查询文本，不处理图片、画像、摘要或查询改写。

后台按本群相邻消息建立有界原文片段，关键词由 FTS5 检索，语义由 sqlite-vec 余弦距离检索，再融合两路排名。每次最多注入五个片段，只在已决定调用主聊天模型且有可用查询文本时检索，判定和旁观消息不增加同步检索。候选先限定本群、本次事件之前和滚动 30 天有效期，并排除近期窗口、当前消息和直接引用中的重复记录。检索和 embedding 共享 `embedding.timeout_seconds` 的有限等待预算；失败或超时记录原因，聊天可继续使用近期上下文。

拍一拍请求要求主聊天模型的正文增量聚合为 JSON 文本，例如 `{"text":"怎么啦？","poke":false}`；`text` 必须是字符串，`poke` 必须是布尔值，至少选择非空文字或回拍之一。完整有效后才执行文字与回拍，不在流接收期间提前执行。正文与动作决策分开，普通聊天中的文字不会被解释为回拍指令。程序只向本次事件群内的发起者回拍，不开放任意群或成员参数；无需新增回拍配置项。

| 模型参数 | 含义与默认值 |
| --- | --- |
| `chat_llm.reply_probability` | 判定为非明确应答或判定失败后的插话概率，范围 0 到 1，默认 `0.1`；设为 0 仍允许直接唤醒及判定通过后的聊天 |
| `chat_llm.max_messages` / `judge.max_messages` | 最多使用的时间线记录数，默认 120 / 12；固定职责和背景另外占两条 API 消息，仍计入总输入预算 |
| `chat_llm.context_tokens` / `judge.context_tokens` | 输入与输出的估算总 token 预算，默认 32000 / 4000；各自先预留 `max_tokens` 的输出空间 |
| `chat_llm.retrieval_context_tokens` | 检索资料的估算输入 token 上限，默认 2048，同时受主聊天总预算限制 |
| `chat_llm.max_tokens` / `judge.max_tokens` | 输出 token 限制；主模型沿用必填配置，示例 3200，判定默认 16 |
| `chat_llm.timeout_seconds` / `judge.timeout_seconds` | 各自请求超时秒数，默认 60 / 5 |

两个窗口和预算都必须为正，判定窗口及预算不能大于主模型，各自总预算必须为输出和完整输入留出有效空间。检索预算必须为正，并小于主聊天扣除输出预留后的空间。估算包含完整静态提示词、机器人身份、消息元信息、文本、媒体标记、检索资料和实际附带图片的视觉开销；ASCII 按每四字符约一个 token、非 ASCII 按每码点两个 token 估算，另计消息结构开销，每张图片按 4096 token 估算，图片解析使用服务默认方式。图片 URL 的字节长度不作为视觉开销。该估算不增加计数网络请求，也不等同于服务商实际计费；预算应与所用模型的上下文容量匹配。

构造请求时，完整静态提示词、当前消息和能够取得的直接引用优先保留，再在消息窗口和 token 预算内选择近期完整消息。较早消息按整条记录移除，不生成历史摘要，不截短当前问题或直接引用。必需输入自身超预算时，直接唤醒返回明确提示，普通插话跳过；判定输入超预算时继续进入既有概率筛选，后续聊天仍独立检查自身预算。所有配置在启动时加载，修改后重启生效。

## NapCat 接入与启动

以下说明首次接入与前台运行；s0 使用已有 NapCat 配置和 `qqbot` 服务。这里有两个方向的 HTTP 连接：

1. PPBot 调用 NapCat：将 `server.host`、`server.port` 配置为 NapCat 的 HTTP API 地址，`server.access_token` 与其令牌一致。请求以 `Authorization: Bearer ...` 发送。
2. NapCat 上报给 PPBot：将上报目的地配置为 PPBot 可达的 `http://主机:client.port/`，使用 HTTP POST，消息段格式为 `array`。`client.host` 是绑定地址；示例中的 `0.0.0.0` 表示监听所有接口，目的地址应填写 NapCat 实际可访问的主机地址。

拍一拍依赖 NapCat 上报带群号的 `notice/notify/poke` 通知，并提供 `/group_poke` API。只接收其他成员拍本机器人的群通知；拍其他成员、机器人自身发起、私聊拍一拍及其他通知均不触发回复。回拍与文字分别检查 NapCat 的 HTTP 和业务结果，只有成功部分进入群时间线，失败不自动重试。

PPBot 不校验 `client.access_token`，填写该字段并不会使接收端具备鉴权。监听地址及网络访问范围需要与此事实一致。

将 `file.cache_path`、`file.data_path` 和 `log.file.path` 配置为实际可写路径。程序自动创建缓存目录、数据目录及其 `AiModule` 子目录；日志父目录需在启动前准备。若配置路径均指向项目内的 `cache/`、`data/`、`log/`，从项目根目录执行：

```sh
mkdir -p log
./release/bot
```

以上是前台运行方式。s0 的服务由现有 systemd 配置管理，仓库不包含该服务定义或日志轮转配置。配置读取失败、监听失败和第三方响应异常需要结合控制台输出及代码检查，进程启动本身不代表所有功能已经可用。

发送下载视频时，PPBot 与 NapCat 必须能读取相同绝对路径。双方在不同机器或容器时，需要已有的共享文件路径安排，程序不会将本地视频上传给 NapCat。

## 数据目录与停机

| 位置 | 内容与生命周期 |
| --- | --- |
| `file.cache_path` | B 站视频缓存；同名文件复用，下载前可能清理目录中的普通文件 |
| `file.data_path/AiModule/messages.sqlite3` | 群消息持久化来源，包含滚动 30 天原文、引用与媒体信息、检索片段、关键词和向量索引、迁移及索引状态；SQLite 运行时可能伴随同名 `-wal`、`-shm` 文件 |
| `file.data_path/AiModule/group_timeline.json` | 旧群时间线；首次合法迁移成功后停用，原文件保留，不自动删除 |
| `file.data_path/AiModule/session_round_counter.json` | 已停用的成员总结计数，不再读取、校验或写入 |
| `file.data_path/AiModule/session_memory.json` | 旧个人历史，原样保留；当前程序不读写或迁移 |
| `file.data_path/AiModule/group_round_counter.json` | 已停用的群总结计数，不再读取、校验或写入 |
| `file.data_path/AiModule/persona_map.json` | 已停用的群人格，不再读取、校验或写入 |
| `file.data_path/AiModule/users_profile_map.json` | 已停用的成员画像，不再读取、校验或写入 |
| `log.file.path` | 追加写入的运行日志，无自动轮转 |

空部署直接建库。存在合法 `group_timeline.json` 时，首次启动在一次事务中导入保留期内的记录并保存迁移完成标记，保留消息来源和顺序；旧的合法 JSON `null` 或 `{}` 视为空状态，缺少事件类型的旧记录按普通消息读取。迁移成功后不再读取、校验或写入旧时间线，重启不重复导入。尚未迁移的旧时间线为空字节、JSON 损坏或结构错误时，或数据库损坏时，程序报告错误并拒绝启动，不以空数据覆盖。四个停用的画像、人格和计数文件即使损坏，也不影响启动；它们及旧个人历史都不导入数据库。

近期时间线在启动时从 SQLite 恢复，默认聊天窗口 120 条、判定窗口 12 条。请求裁剪和内存窗口淘汰不改写有效归档。原文与关联片段、关键词和向量索引按滚动 30 天同步清理；清理尚未执行时，过期内容也不能由时间线、直接引用或检索进入请求。自动清理只处理运行中的归档和索引，不删除停用的 JSON 文件。

若要手工清理旧文件，先在实际 `file.data_path/AiModule` 目录确认迁移标记：

```sh
sqlite3 -readonly messages.sqlite3 "SELECT value FROM metadata WHERE key='timeline_migrated';"
```

输出 `1` 表示迁移事务已经完成。核对重启后的近期消息与引用后，可以在该目录手工删除 `group_timeline.json`、`persona_map.json`、`users_profile_map.json`、`session_round_counter.json` 和 `group_round_counter.json`，例如：

```sh
rm -- group_timeline.json persona_map.json users_profile_map.json session_round_counter.json group_round_counter.json
```

只删除实际存在且已确认不再需要的文件；`session_memory.json` 不参与迁移，是否保留由用户决定。不要删除运行中的 `messages.sqlite3` 及其 SQLite 配套文件，也不要将需要保留的资料放进缓存目录。

普通群消息即使没有触发聊天，也先进入近期时间线和待归档队列；机器人出站只在 NapCat 确认成功后加入。保存线程按 `file.save_frequency_seconds` 周期增量批量提交，示例中的 10 秒不代表实际部署值。没有新记录时不提交空写入。每批使用事务，失败时保留该批记录供后续周期重试，期间到达的新消息不会被旧批次标记为已提交。索引在线程中另行处理，失败或尚未完成不会丢失归档原文，服务恢复后继续。

正常停止使用 `SIGTERM` 或 `SIGINT`；systemd 的正常停止与重启会经过同一保存路径。程序先停止接入，等待在途 HTTP 处理结束，再提交剩余消息并停止后台索引；不要求等待未完成索引全部成功。`TimeoutStopSec` 应容纳配置中的判定、检索、聊天及 NapCat 发送等实际在途操作，不能把默认 3 秒的 embedding 超时视为整个进程的停机时限。

在 s0 停止并确认结果：

```sh
ssh s0 'sudo systemctl stop qqbot && systemctl show qqbot -p ActiveState -p Result -p ExecMainStatus'
ssh s0 'sudo journalctl -u qqbot -n 100 --no-pager'
```

正常完成时进程应退出，`ActiveState=inactive`、`Result=success`、`ExecMainStatus=0`。最终提交失败会记录 `正常停止时群消息最终归档失败` 并以非零状态退出，不能只凭等待一个周期判断保存成功。重新启动使用 `sudo systemctl start qqbot`。异常终止允许丢失尚未提交的消息；周期保存正常时，丢失范围为最近一个保存周期。

归档与日志会明文保存消息、成员信息和图片 URL，配置含服务密钥。未 @ 的文本与媒体类型标记可能发送给判定服务，选中的近期与检索资料会发送给主模型，索引原文和查询文本会发送给 embedding 服务。主模型仅接收当前消息与直接引用的原图地址。PPBot 不下载或持久化图片文件，不转 Base64；URL 缺失或不是 HTTP(S) 时保留不可读取标记，URL 失效时不保证后续能够读图。

## 日志排查

`log.file.level` 和 `log.console.level` 分别控制文件与控制台输出，沿用 0 DEBUG、1 INFO、2 WARN、3 ERROR，记录配置级别及以上的日志。日常可设为 1，查看消息收发、直接唤醒、判定及概率筛选摘要与错误；需要查看消息、回复正文时，将对应输出设为 0，修改配置后重启生效。s0 的控制台输出由 journal 收集，文件输出写到 `log.file.path`，两者的日志内容一致，控制台另有级别颜色。

聊天分流的 INFO 日志包含群号 `group` 和消息 ID `message`。`Chat LLM 直接唤醒` 的 `reason` 为 `at`、`reply` 或 `poke`；`回复判定结果` 仅记录有效的 `YES` 或 `NO`。`Chat LLM 概率筛选` 中的 `probability` 为配置概率，`matched` 表示是否命中；未命中时直接沉默，命中后主模型仍可返回 `[SILENT]`，此时记录 `Chat LLM 概率聊天选择沉默`。这些摘要不含正文，可以在 INFO 级别区分没有触发聊天和模型主动选择沉默。

一条 HTTP 错误日志包含操作名、HTTP 状态、原因和可提取的服务错误码、消息或请求 ID。错误详情最多 1536 个 UTF-8 字节；非 JSON 错误体也会安全保留摘要。以下摘自日志测试的本地模拟场景，省略时间和模型名，不代表真实外部服务的运行结果：

```text
[WARN] 回复判定 http=429 reason=HTTP 响应异常，进入概率筛选 detail=code=1305 message=quota-from-judge request_id=judge-request-id
```

先根据操作名区分判定、聊天、embedding、历史检索或归档，再结合 HTTP 状态和服务返回原因排查配额、鉴权、限流、索引和磁盘异常。HTTP 200 也可能包含业务失败或无效字段，日志会说明对应原因。网络错误单独记录连接或超时原因；判定失败保留一次 WARN，不生成虚假的 `NO` 判定结果，并继续记录概率筛选，不重试。概率未命中和模型选择沉默不是错误，通过 INFO 摘要观察。

文件读写失败记录路径和具体系统或 JSON 原因；下载日志区分网络、HTTP、超限与磁盘写入失败。配置文件无法打开、JSON 无效或监听失败时，进程记录启动错误并以状态码 1 退出；日志文件自身无法写入时仍向标准错误报告。

所有日志按单行输出，JSON 使用紧凑格式，换行等控制字符转义。已配置的 API 密钥和访问令牌值会脱敏；群号、发言人等摘要信息仍会保留，DEBUG 正文和数据文件也仍可能包含明文群聊内容，不能将密钥脱敏视为全部敏感数据已清洗。

## 手工验证

先用 `make test` 验证可控分支，再按下表验证真实接入。模型对呼叫、追问和成员间对话的语义判断需要真实配置与样例评估；外部功能也需要对应服务和 NapCat 配合。

命令推荐格式为 `@机器人 /命令 参数`，其中 `@机器人` 表示实际指向本机器人的 @ 消息段，手工输入同样文字不能代替。@ 可以出现在命令文本前后；命令名与参数之间使用 ASCII 空格。发送 `@机器人 /帮助` 可查看七条命令及调用格式。直接发送的单段纯文本响应引用本次命令消息，缺少有效消息 ID 时只发文本；图片合并转发和点歌语音不附加引用。

| 操作 | 应观察的结果 |
| --- | --- |
| 在群里发送 `@机器人 /帮助`、`@机器人 /时间` | 返回七条带 `/` 前缀的命令及调用格式、主机本地时间；文本引用本次命令消息，不调用模型 |
| 在群里发送 `@机器人/时间`、`/时间 @机器人`，或在命令文本前加入普通空格 | 均执行时间命令 |
| 在群里发送 `@机器人 /天气`、`@机器人 /点歌` | 缺少参数的文本提示引用本次命令消息，无需访问对应外部服务；天气提示使用新调用格式 |
| 发送 `时间`、`/时间`、`@机器人 时间`、`@机器人 /未知命令`，或在 `/时间` 前加入正文 | 不执行命令，继续卡片或聊天分流；显式 @ 的文本可直接进入聊天，不保证沉默 |
| 发送普通非命令文本，不 @ 机器人 | 消息进入本群时间线；判定通过时回复，否则进入配置的概率筛选，概率插话允许沉默 |
| 私聊机器人 | 不产生业务回复，不进入群时间线 |
| 群聊中仅 @ 机器人，没有文本和图片 | 绕过判定和概率，直接调用主模型；完整生成后回复引用本次消息，消息 ID 无效时只发文本 |
| 群聊中 @ 后发送普通问题或一张、多张图片 | 绕过判定和概率，主模型收到文字及可用图片；回复引用本次触发消息，不额外 @；NapCat 确认成功后回复进入时间线 |
| 不 @，引用已记录的机器人回复提问或发送图片 | 绕过判定和概率，主模型收到对应内容；回复仅含文本，不主动引用或 @ |
| 不 @，仅引用已记录的机器人回复，没有文本和图片 | 同样绕过判定和概率，直接调用主模型；完整生成后仅回复文本 |
| 机器人回复后发送无 @ 的补充或“那第二种呢？” | 判定输入包含近期成员与机器人发言，由判定服务结合上下文决定是否明确需要回应 |
| 群成员相互讨论相同话题，或仅提及机器人而未请求参与 | 判定应为 `NO`，进入概率筛选；可先将概率设为 0 观察沉默，避免将概率插话误判为判定通过 |
| 甲提供图片后乙向机器人提问，另在其他群发言或发送图片 | 未明确引用时，甲的图片只保留媒体标记；明确引用甲的原消息时，主模型可接收该图，来源身份可区分，不混入其他群记录或图片 |
| 图片回复后发送没有引用原图的纯文本追问 | 不再次附带历史原图；需要重新看图时明确引用原消息 |
| 明确引用本群已从内存淘汰、仍在保留期内的消息 | 从 SQLite 取得原记录；引用已确认机器人回复时直接唤醒，引用其他成员仍按既有判定和概率分流 |
| 引用不存在、已过期、晚于当前事件或仅属于其他群的消息 | 保留引用不可用标记，不跨群、不拉取 NapCat 历史、不追溯更早引用 |
| 完整静态提示词、当前问题和直接引用合计超过预算 | 不发出主模型请求；直接唤醒提示超预算，普通插话跳过，必需内容不被截短 |
| 群聊中发送 `/问题`，可附图片 | 与普通文本使用相同分流及群上下文，图片作为图文输入，没有单次图文入口 |
| 未直接唤醒时发送纯图片 | 进入判定与概率分流，判定只看到文字和类型标记；触发聊天时主模型收到图片，不返回输入提示 |
| 未直接唤醒时发送没有文本和图片的语音等消息 | 只记录类型及可用文本，不请求模型或发送输入提示 |
| 图片 URL 缺失、失效或主模型服务拒绝图片 | 缺 URL 时请求保留不可读取标记；读图请求失败时，直接唤醒返回失败提示，普通路径沉默，不伪造成功内容 |
| 群成员拍本机器人 | 跳过判定和概率，模型结合群语境选择文字、回拍或两者；纯回拍也算回应，文字不主动 @ 或引用 |
| 主模型流式生成期间观察 QQ，并测试中断、超时或缺少结束事件 | 完整结束前不发送正文或回拍；失败不发送半截正文、不执行回拍，直接唤醒尝试发送失败提示，普通路径沉默，不重试或回退 |
| 拍其他成员、自身发起、私聊拍一拍或其他通知 | 不调用模型、不回复；机器人回拍产生的自身通知不触发循环 |
| 选择文字与回拍后使其中一项发送失败 | 群时间线只保留实际成功部分，回拍记录动作、目标和时间，不伪造普通消息 ID，不自动重试 |
| 配置外部服务后发送 `@机器人 /天气 北京`、`@机器人 /吃啥`、`@机器人 /随机二次元图片`、`@机器人 /来点涩图`、`@机器人 /点歌 歌曲名称` | 分别收到文本、合并转发图片和语音段等对应结果 |
| 分享符合配置应用 ID 的 B 站卡片 | 收到封面与视频信息；下载成功且路径可读时另收到视频 |
| 使判定返回 `NO` 且概率设为 0，发送普通消息并确认保存后重启 | 从 SQLite 恢复本群近期顺序与引用；旧画像、人格、计数和个人历史文件保持原样，不触发总结 |
| 各群分别积累旧话题，当前群用中文关键词或不同措辞追问 | 只取得本群、当前事件之前且在 30 天内的相关原文，最多五个有来源片段，不重复近期消息，不自动附图 |
| 检索没有相关命中，或近期历史与检索资料合计接近预算 | 不强塞无关片段；限制检索及普通历史，完整保留静态提示词、当前问题和直接引用 |
| embedding 服务失败或超时后恢复 | 失败记录可见，归档原文保留，聊天可仅用近期上下文继续，后台随后继续索引 |
| 正常停止、重启，或使最终数据库写入失败 | 正常停止提交未归档消息；最终提交失败明确记录并非零退出，重启不重复迁移旧时间线 |

需要区分上报处理、NapCat 发送确认和 QQ 送达：PPBot 返回 `{}` 只说明上报处理已经返回；发送层检查 NapCat 的 HTTP 与业务结果后才记录机器人回复，但不提供 QQ 端送达保证。发送失败记录在日志中，没有重试。排查时先核对两个 HTTP 方向、配置路径和目录，再检查相应外部接口的协议及响应字段。
