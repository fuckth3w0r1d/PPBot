# 开发与运行指南

本指南说明当前源码的构建、配置、s0 部署和验证方法。当前 AI 使用单聊天模型、独立判定服务和共享群时间线，行为及验收要求见 [需求规格](../spec.md)。模块和数据关系见 [架构说明](../map.md)，其他文档见 [导航](../README.md)。

## 构建环境

需要支持 C++17 的 `g++`、GNU Make、OpenSSL 开发头文件及库、线程库。仓库已包含 `include/httplib.h` 和 `include/json.hpp`，不需要另行下载这两个头文件。

根 README 记录的原项目环境为 Ubuntu 24.04、GCC 13.3、OpenSSL 3.0.13 和 NapCat 4.17.29。这些是已有环境记录，不是最低版本约束或当前机器的验证结果。

在项目根目录执行：

```sh
make
```

构建自动收集 `src/` 下的 `.cpp`，以 C++17 和 `-O2` 编译，将对象文件与依赖文件保存在 `release/` 对应目录，链接 `ssl`、`crypto` 和 `pthread`，生成 `release/bot`。`make clean` 会删除整个 `release/` 目录。仓库现有二进制不能替代本地源码构建的验证。

聊天功能的本地模拟验收执行：

```sh
make test
```

该目标编译 [tests/chat_test.cpp](../../tests/chat_test.cpp)，产物为 `release/tests/chat_test`。测试启动本地 HTTP 模型和 NapCat 模拟服务，通过固定判定结果及 0、1 概率检查分流、请求内容、持久化与失败路径，不需要真实模型密钥。它不验证真实模型的语义效果或 QQ 送达，后者按下文手工验证。

## s0 部署与实测更新

项目部署在服务器 `s0`，通过 `ssh s0` 连接。NapCat 和服务配置已经就绪。更新程序前先核对下文的 AI 配置：使用旧版 `ai2` 配置的部署需要新增独立 `judge` 配置，填写实际判定服务地址、模型和密钥；`ai2` 不再读取。普通插话概率由 `ai.reply_probability` 控制，默认及示例为 `0.1`。其余已有配置和运行数据继续使用，不清理旧个人历史文件。

二进制使用 `scp` 经 SSH 传输本地 `release/bot`，不同步源码，不在服务器仓库执行 `git push`、`git pull` 或 `git checkout` 等代码更新操作。配置准备完成后再重启服务。

systemd 服务名为 `qqbot`，服务定义位于 `/etc/systemd/system/qqbot.service`。服务以 `r3t2` 用户运行 `/home/r3t2/PPBot/release/bot`，即 `~/PPBot/release/bot`；工作目录为 `/home/r3t2`，配置中的相对文件路径以该目录为基准。标准输出和标准错误写入 journal。

本地构建环境需要与 s0 的处理器架构和动态库版本兼容。更新前先按下文“数据目录与停机”确认 AI 数据已成功落盘；程序没有退出前最后保存逻辑。随后在本地项目根目录执行：

```sh
make &&
scp release/bot s0:~/PPBot/release/bot.new &&
ssh s0 'mv ~/PPBot/release/bot.new ~/PPBot/release/bot && sudo systemctl restart qqbot'
```

构建成功后才上传产物。上传文件暂存为同目录的 `bot.new`，完成后通过重命名替换二进制，再重启服务，避免直接覆盖正在执行的文件。更新后查看服务状态和日志，并按本文“手工验证”中的场景检查实际回复：

```sh
ssh s0 'systemctl status qqbot --no-pager'
ssh s0 'sudo journalctl -u qqbot -n 100 --no-pager'
```

## 配置文件与加载路径

以下用于首次准备运行环境；已有部署按模板补齐判定服务配置。模板的实际文件名是 [config.example.json](../../config.example.json)。从项目根目录准备配置：

```sh
cp config.example.json config.json
```

复制后还不能直接启动。当前 [config.h](../../include/config.h) 中 `load_config` 的默认路径是 `/home/r3t2/PPBot/config.json`，[main.cpp](../../src/main.cpp) 没有传入其他路径。程序不会自动读取当前工作目录中的 `config.json`，也没有命令行或环境变量覆盖入口。必须将配置放在该路径，或者在开发时修改头文件中的默认路径后重新 `make`。

配置解析直接读取各项字段，缺少字段、类型不符或 JSON 无法解析可能导致启动失败。所有配置块都需要按 [config.cpp](../../src/config.cpp) 的读取方式提供；当前没有关闭某一功能后省略对应配置的机制。修改配置后需要重启进程。

| 配置块 | 用途与填写要求 |
| --- | --- |
| `log` | 日志文件路径、文件与控制台级别；级别为 0 DEBUG、1 INFO、2 WARN、3 ERROR，输出配置级别及以上日志 |
| `bot` | `qq` 使用字符串，与 NapCat 机器人账号一致；`name` 为模型输入中的机器人名称，默认 `Bot` |
| `server` | NapCat HTTP API 的主机、端口、访问令牌；PPBot 通过 HTTP 调用该地址 |
| `client` | PPBot 接收上报的监听地址与端口；`access_token` 会被读取，但不执行入站校验 |
| `ai` | 唯一聊天模型及画像、人格总结服务；包含地址、模型、密钥、人设、预算、超时和插话概率 |
| `judge` | 独立判定服务；必须提供 `host`、`path`、`model`、`key`，另有独立端口、超时和短上下文预算 |
| `amap` | 天气服务主机、HTTPS 端口、请求路径和密钥 |
| `b23` | 卡片应用 ID、B 站 HTTPS 主机和查询、播放路径 |
| `file` | 缓存与数据路径、单次下载字节上限、缓存文件数量、下载缓冲字节数、保存间隔秒数 |
| `random_img` | HTTPS 图片服务，响应需要 `url` 字段 |
| `random_img2` | HTTP 图片服务，代码在路径后附加 `?tag=`，响应需要 `proxyUrls` 字符串数组 |
| `eat` | HTTPS 餐食服务，响应需要 `mealwhat` 字段 |
| `music` | HTTP 音乐搜索与直链服务，依次读取 `result.songs[0].id` 和 `data[0].url` |

示例中的密钥和文件路径必须按运行环境填写。`random_img2` 的示例与 `random_img` 指向相同服务，但二者的客户端协议和响应字段要求不同，不能据此认定两个图片命令都可用；实际配置需匹配代码要求。其他外部服务同样依赖响应格式，示例地址不代表服务已经验证可用。

`ai` 与 `judge` 都使用 Chat Completions 格式。`host` 可填写带 `http://` 或 `https://` 的主机地址，省略协议时使用 HTTPS；没有显式端口时使用对应 `port`，API 路径单独填写在 `path`。判定服务只输出 `YES` 或 `NO`，不作为聊天备用服务。

| AI 参数 | 含义与默认值 |
| --- | --- |
| `ai.reply_probability` | 判定为非明确应答或判定失败后的插话概率，范围 0 到 1，默认 `0.1`；设为 0 仍允许直接唤醒及判定通过后的聊天 |
| `ai.max_messages` / `judge.max_messages` | 最多使用的时间线记录数，默认 120 / 12；固定职责和背景另外占两条 API 消息，仍计入总输入预算 |
| `ai.context_bytes` / `judge.context_bytes` | 总字节预算，默认 64000 / 12000；先扣除 `4 * max_tokens` 输出预留，剩余部分限制完整序列化 `messages` 的 UTF-8 字节数 |
| `ai.max_tokens` / `judge.max_tokens` | 输出 token 限制；主模型沿用必填配置，示例 3200，判定默认 16 |
| `ai.timeout_seconds` / `judge.timeout_seconds` | 各自请求超时秒数，默认 60 / 5 |
| `ai.max_rounds` | 总结计数的基数，达到 `max(1, max_rounds / 10)` 后，在下一次进入聊天路径时总结；它不再控制个人问答历史长度 |

两个窗口和预算都必须为正，判定窗口及预算不能大于主模型。预算包含人设、画像、身份和消息内容；超长输入会裁剪，无法容纳固定职责和必要身份时不发出请求。字节预算不是服务商的精确 token 计算，实际值需与所用模型的上下文容量匹配。所有配置在启动时加载，修改后重启生效。

## NapCat 接入与启动

以下说明首次接入与前台运行；s0 使用已有 NapCat 配置和 `qqbot` 服务。这里有两个方向的 HTTP 连接：

1. PPBot 调用 NapCat：将 `server.host`、`server.port` 配置为 NapCat 的 HTTP API 地址，`server.access_token` 与其令牌一致。请求以 `Authorization: Bearer ...` 发送。
2. NapCat 上报给 PPBot：将上报目的地配置为 PPBot 可达的 `http://主机:client.port/`，使用 HTTP POST，消息段格式为 `array`。`client.host` 是绑定地址；示例中的 `0.0.0.0` 表示监听所有接口，目的地址应填写 NapCat 实际可访问的主机地址。

PPBot 不校验 `client.access_token`，填写该字段并不会使接收端具备鉴权。监听地址及网络访问范围需要与此事实一致。

将 `file.cache_path`、`file.data_path` 和 `log.file.path` 配置为实际可写路径。程序自动创建缓存目录、数据目录及其 `AiModule` 子目录；日志父目录需在启动前准备。若配置路径均指向项目内的 `cache/`、`data/`、`log/`，从项目根目录执行：

```sh
mkdir -p log
./release/bot
```

以上是前台运行方式。s0 的服务由现有 systemd 配置管理，仓库不包含该服务定义或日志轮转配置。配置读取失败、监听失败和第三方响应异常需要结合控制台输出及代码检查，进程启动本身不代表所有功能已经可用。

发送下载视频时，PPBot 与 NapCat 必须能读取相同绝对路径。双方在不同机器或容器时，需要已有的共享文件路径安排，程序不会将本地视频上传给 NapCat。

## 数据目录与停机

| 位置 | 内容与生命周期 |
| --- | --- |
| `file.cache_path` | B 站视频缓存；同名文件复用，下载前可能清理目录中的普通文件 |
| `file.data_path/AiModule/group_timeline.json` | 按完整群号保存的共享时间线，保留配置窗口内的消息及成功发送回复 |
| `file.data_path/AiModule/session_round_counter.json` | 按群和成员累计的成功回复计数，用于画像总结 |
| `file.data_path/AiModule/session_memory.json` | 旧个人历史，原样保留；当前程序不读写或迁移 |
| `file.data_path/AiModule/group_round_counter.json` | 群人格总结的轮数计数 |
| `file.data_path/AiModule/persona_map.json` | 各群的机器人格 |
| `file.data_path/AiModule/users_profile_map.json` | 各群用户的昵称、群昵称和画像描述 |
| `log.file.path` | 追加写入的运行日志，无自动轮转 |

首次运行时，数据文件不存在可从空状态开始；原有群人格、成员画像及计数继续加载。旧的合法 JSON `null` 或 `{}` 视为空状态；空字节文件、损坏 JSON 或非空结构错误会使启动失败，不会按空数据覆盖原文件。新时间线只积累上线后收到的消息，不拉取历史，也不将旧个人历史拼接成群聊顺序。

不要将其他需要保留的普通文件放进缓存目录，清理不会识别其业务用途。AI 数据与日志以明文保存消息和用户信息，配置中包含服务密钥。未 @ 的普通文本也会发送给判定服务；主模型接收选取的本群历史和画像。

群消息收集和人格、画像等状态变化后，保存线程按照 `file.save_frequency_seconds` 周期写入五个当前数据文件。没有触发 AI 的普通群消息也进入保存范围；状态未变化时不重复写入。写入失败会跳过该轮后续文件，并保留待保存状态，多文件写入不是事务。停止前需要等待保存周期并确认文件已成功更新；仅等待时间不能证明保存成功。

进程没有退出前最后保存逻辑，也没有信号停机处理。停止或崩溃可能丢失尚未落盘的状态，写入中断也可能影响文件完整性。下一次启动只能恢复实际成功写入且格式符合读取要求的数据。

## 手工验证

先用 `make test` 验证可控分支，再按下表验证真实接入。模型对呼叫、追问和成员间对话的语义判断需要真实配置与样例评估；外部功能也需要对应服务和 NapCat 配合。

| 操作 | 应观察的结果 |
| --- | --- |
| 在群里直接发送 `帮助`、`时间` | 返回命令列表和主机本地时间；无需 @ |
| 在群里发送 `天气`、`点歌` | 返回缺少参数的提示，无需访问对应外部服务 |
| 发送普通非命令文本，不 @ 机器人 | 消息进入本群时间线；判定通过时回复，否则进入配置的概率筛选，概率插话允许沉默 |
| 私聊机器人 | 不产生业务回复，不进入群时间线 |
| 群聊中仅 @ 机器人 | 返回输入提示 |
| 群聊中 @ 后发送普通问题，或引用已记录的机器人回复提问 | 绕过判定和概率，使用主模型；NapCat 确认发送成功后回复进入群时间线 |
| 机器人回复后发送无 @ 的补充或“那第二种呢？” | 判定输入包含近期成员与机器人发言，由判定服务结合上下文决定是否明确需要回应 |
| 甲提供信息后乙向机器人提问，另在其他群发言 | 主模型看到当前群窗口内甲、乙的不同身份与原文，不混入其他群历史、人格或画像 |
| 群聊中发送 `/问题`，可附图片 | 与普通文本使用相同分流及群上下文；图片只有类型标记和可用文本，没有单次图文入口 |
| 未直接唤醒时发送纯图片、语音等 | 只记录类型及可用文本，不请求模型或发送输入提示 |
| 配置外部服务后测试天气、餐食、图片和点歌 | 分别收到文本、合并转发图片和语音段等对应结果 |
| 分享符合配置应用 ID 的 B 站卡片 | 收到封面与视频信息；下载成功且路径可读时另收到视频 |
| 使判定返回 `NO` 且概率设为 0，发送普通消息并确认保存后重启 | 后续主模型请求仍可读取窗口内已保存的群消息；旧个人历史文件保持原样 |

需要区分上报处理、NapCat 发送确认和 QQ 送达：PPBot 返回 `{}` 只说明上报处理已经返回；发送层检查 NapCat 的 HTTP 与业务结果后才记录机器人回复，但不提供 QQ 端送达保证。发送失败记录在日志中，没有重试。排查时先核对两个 HTTP 方向、配置路径和目录，再检查相应外部接口的协议及响应字段。
